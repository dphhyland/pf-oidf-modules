Device-anchored agent identity

An agent on your phone proves three things — or it gets nothing.

A genuine build, on genuine hardware. A human who authenticated recently. Possession of a key that never leaves the enclave. None of the three stands in for either of the others — and only when all three line up does the platform mint a short-lived credential the agent can actually use.

The big picture

From an install, to a token an agent can act on.

One journey, five stops. A phone install becomes an enrolled instance the moment it proves what it is; the platform mints a credential for it; the agent presents that credential and walks off with a sender-constrained token. The gold stop is the one this page is about — and PingOne can pull the rug out from under any point past it, at any time.

Three primitives, none interchangeable

iOS forces this split — one proof each, and only one that can sign.

App Attest's key is sealed and its output is CBOR; it can't sign our JWS. AuthenticationServices never hands over a passkey's private key either. Only the Secure Enclave key can actually sign anything — so the other two exist purely to vouch for it.

App Attest

Attests a genuine, unmodified build of the app on genuine Apple hardware. Can't sign our JWS — its key is sealed, its output is CBOR.

PingOne passkey

Attests which human is present, at what assurance, and when. Can't sign our JWS — the OS never exposes a passkey private key.

Secure Enclave key

Attests possession, device-bound, non-extractable. The only one that signs — ES256, gated by biometry.

The bridge

App Attest can't attest a key the app made itself — so it commits to it instead.

clientDataHash =
SHA-256( enclave JWK thumbprint ‖ challenge )

The app commits this hash as App Attest's clientDataHash. The attester recomputes it independently from the key and challenge it holds — so a mismatch surfaces as nonce_mismatch, not something taken on trust. This proves a genuine app asked us to certify a key. It does not prove the key is in hardware — the EUDI wallet spec considered and rejected this exact binding for that reason. Android's Key Attestation doesn't have this gap; Apple gives us nothing better.

The ceremony

Once, with a human present. Then quietly, on its own.

Enrolment happens once, and it's the only step that needs the human. Everything after re-mints on the hot path with no prompt at all, for as long as the platform's own trust in the last authentication holds.

generate

The key

The Secure Enclave mints a P-256 key with .biometryCurrentSet — it never leaves, and a biometric re-enrolment invalidates it.

prove

Three proofs, once

App Attest binds the build; the passkey binds the human; the commitment binds them both to this key.

mint

The attestation

The attester verifies the chain, verifies the human, writes one registry row, and mints a 15-minute Client Attestation.

renew

Quietly, from here

The agent re-mints on the hot path — no prompt — until the server's own record of the last authentication ages out.

→The subject in every attestation is an opaque instance id. Never the human, never the device — so no token, anywhere downstream, can become a permanent cross-service handle on a person.

Who's actually enforcing what

The phone's window is UX. The server's check is the control.

Apple documents no expiry on a pre-authenticated LAContext — so a compromised app could hold one indefinitely, and the signature alone can't prove otherwise. Saying that plainly is what keeps the real control where it belongs.

app-enforced

The client-side window is UX, not security

The app chooses to stop signing after a while. That's a courtesy to the user, not a guarantee to anyone verifying the result.

server-enforced

uv_last_verified_at is the real control

Checked on every mint. Once it ages out — five minutes by default — re-minting is refused with user_verification_required, no matter what the phone would have signed.

fails closed

Development App Attest is refused by default

Accepted only when explicitly configured, and every enrolment made that way is flagged in the registry so it can never later pass as production.

fails closed

Unknown compliance can't mint

A device that's never been assessed is treated the same as one that failed. Never-assessed is not the same as clean.

The revocation path

PingOne says the device fell out of line. The agent finds out the hard way.

No push to the device, no waiting for the attestation to expire, no re-authentication. The next mint just fails — and coming back into compliance doesn't quietly undo it, because a healthy device says nothing about whether the owner is actually there.

The demo

One thing this can't fake. Everything else is real.

App Attest only verifies against a chain rooted at Apple's real root CA, and only a physical iPhone can produce one. So the demo server trusts a different, openly-checked-in root instead — the one substitution in an otherwise real stack.

Real

  • Postgres, schema applied, real registry writes
  • The actual server wiring — Main.java's own code
  • PingOne, genuinely verifying the ID token
  • The full HTTP ceremony, over a real socket

Synthetic

  • The App Attest trust root — a bundled, openly-checked-in key
  • Not Apple's — nothing but hardware can produce that one

There's no browser view — this is a CLI walking a JSON API, exactly like the phone will. This is what running it actually looks like:

than guessing. Pass a real one with --id-token to see the green path.

How to run it yourself:

1

Open Docker Desktop, then docker compose -f deploy/device-enrolment/docker-compose.yml up --build — real Postgres and the demo server come up on :8180, wired to the real PingOne tenant.

2

mvn -pl demo/phone-simulator -am -DskipTests package once, to build the CLI.

3

Run PhoneSimulatorCli --base-url http://localhost:8180 --demo-evidence for the zero-setup run above, or --id-token <a real PingOne ID token> for the full green path.

Full detail, including how to suspend an instance live via the CAEP signal, is in demo/phone-simulator/README.md.

Not a slide — a running system

Three proofs. One credential. Nothing a stolen phone can use alone.

A stolen unlocked phone still can't mint anything past the time-box; a stolen attestation is useless without the enclave key; a stolen key is useless without the phone. That's the whole point of making three parties agree.
